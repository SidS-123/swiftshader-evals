# Toy controls: predicted vs observed

Predictions are in `DESIGN.md`. The table between the markers is generated
from `runs/control-<name>-<split>/report.json` by

```sh
python3 -m evalbase.reports.controls_summary --instance examples/toy --write
```

after

```sh
export EVALBASE_INSTANCE=examples/toy
python3 -m evalbase.corpus.common both
python3 -m evalbase.grader.cli refcache
python3 -m evalbase.grader.cli --corpus examples/toy/corpus/hidden --cache examples/toy/runs/refcache-hidden refcache
for split in public hidden; do
  for c in reference stub half_samples brightness_x2 stale_output; do
    python3 -m evalbase.grader.cli --corpus examples/toy/corpus/$split \
        --cache examples/toy/runs/refcache$([ $split = hidden ] && echo -hidden) \
        control $c --out examples/toy/runs/control-$c-$split --label control-$c-$split
  done
done
```

## Reading the table

`reference` is 1.0 on both splits; `stub` is the null band (0.02, almost all
of it the one procedural check a silent candidate passes for free);
`half_samples` is above 0.9 because the threshold accepts the run that
defined it; `brightness_x2` and `stale_output` lose the whole fidelity
category. The performance-variance table is empty: the toy has no five-run
repeat, and its timed runs are too short for one to mean anything.
