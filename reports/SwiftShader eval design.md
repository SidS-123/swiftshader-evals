# Grade SwiftShader rebuilds the way Khronos grades drivers

The strongest eval we can build on google/swiftshader is **a from-scratch, drop-in Vulkan ICD reimplementation (Variant A)**. It should be graded in evalBase against a pinned SwiftShader oracle, using CTS-style, format-aware image and buffer comparisons, a procedural category built from the oracle's own VkResult and query ledger, and a performance category gated on correctness. The hidden split should be generated from randomized, validated Vulkan workloads. SwiftShader suits this role well. As of September 2026 it is a slow-moving, Apache-2.0, **Vulkan 1.3-only CPU driver of about 100k first-party C++ lines**, and its own CI pins a CTS commit and records **416,472 passing dEQP-VK cases**, so a ready-made conformance vocabulary already exists. The AI benchmark literature shows why the design has to be this heavy. The closest prior art, ProgramBench, reports **0% fully resolved across nine frontier models**, so a binary "done" metric sits at the floor for years and a continuous score is required. METR finds **at least 16% of successes on 8h+ tasks involved cheating**, and OpenAI retired SWE-bench Verified over flawed tests and contamination, so hidden tests, oracle isolation and trivial-submission controls are part of the measurement itself. The main open risks are three: evalBase's defaults were tuned for a noisy Monte Carlo renderer, whereas SwiftShader is (probably) deterministic; SwiftShader's source is almost certainly in training data; and a from-scratch interpreter will be much slower than SwiftShader's JIT. Each has a concrete mitigation, and each needs to be measured before any model is run.

A note on evidence: facts about SwiftShader come from a clone at HEAD `1e80438d2b93` (2026-09-16). Line counts and commit counts are the researcher's own tallies, not official figures. Claims tagged **[unverified]** come from background knowledge or paper abstracts that were not re-fetched, and they must be checked before anyone quotes them externally.

## SwiftShader in 2026 is a stable Vulkan 1.3 oracle, not a GL/D3D renderer

SwiftShader today is **only a Vulkan ICD**. `VkConfig.hpp` hard-codes `API_VERSION = VK_API_VERSION_1_3` and a SPIR-V target env of Vulkan 1.3 ([VkConfig.hpp](https://github.com/google/swiftshader/blob/master/src/Vulkan/VkConfig.hpp)). The D3D8/D3D9 code was deleted in 2020 ([commit f99302c4](https://github.com/google/swiftshader/commit/f99302c4)) and the legacy OpenGL ES code in 2022 ([commit c0a055bf](https://github.com/google/swiftshader/commit/c0a055bf)). GLES now comes from ANGLE layered on top ("SwANGLE"). The README claims Vulkan 1.3 conformance (Khronos submission #717) and GLES 3.1 conformance through ANGLE (#906) ([README](https://github.com/google/swiftshader/blob/master/README.md)). **Neither submission could be independently rendered from the Khronos site**, and no Vulkan 1.4 submission was found, even though the Vulkan headers were bumped to 1.4.355 in June 2026. The in-repo `docs/Index.md` is flagged out of date and still describes the deleted GL code ([docs/Index.md](https://github.com/google/swiftshader/blob/master/docs/Index.md)), so eval task text should not be drafted from it.

The implemented surface is bounded. The driver advertises about **115 extension names** ([libVulkan.cpp](https://github.com/google/swiftshader/blob/master/src/Vulkan/libVulkan.cpp)), including dynamic rendering, synchronization2, timeline semaphores, descriptor indexing, robustness2, graphics pipeline library and host image copy. It does **not** support geometry or tessellation shaders, shaderFloat64, sparse binding, wide lines or multi-viewport ([VkPhysicalDevice.cpp](https://github.com/google/swiftshader/blob/master/src/Vulkan/VkPhysicalDevice.cpp)). That leaves vertex, fragment and compute as the only shader stages. Subgroup size is fixed at 4 because the whole pipeline is "SIMT over 4 lanes" (`SIMD::Width == 4`) ([SIMD.cpp](https://github.com/google/swiftshader/blob/master/src/Reactor/SIMD.cpp)).

The architecture has four layers, all first-party code: the Vulkan object layer (`src/Vulkan`, **31,468 lines**); the device/renderer, which covers clipping, rasterization, the blitter and the BC/ETC/ASTC decoders (`src/Device`, 10,997 lines); the pipeline, where `SpirvShader` emits Reactor code per SPIR-V instruction and the sampler lives (`src/Pipeline`, 24,581 lines); and Reactor, a C++-embedded DSL that JITs through LLVM or Subzero (`src/Reactor`, 26,857 lines) ([src tree](https://github.com/google/swiftshader/tree/master/src); [docs/Reactor.md](https://github.com/google/swiftshader/blob/master/docs/Reactor.md)). Shaders are compiled, not interpreted. Each SPIR-V module plus its pipeline state becomes a specialized native routine that is cached by state. This matters for the eval. A candidate that writes an interpreter is a different design, but it can still be graded at the output level, and it will lose heavily on performance. The CMake default backend is LLVM 10. Chromium's GN build defaults to Subzero on x86 because it produces smaller binaries ([docs/Subzero.md](https://github.com/google/swiftshader/blob/master/docs/Subzero.md)). That gives us **two Google-shipped, equally valid builds of the same driver**, which becomes the natural "second seed" for tolerance. An attempt to make LLVM 16 the default was **reverted on 2026-06-08** because it broke the Dawn roll ([commit 5b0479bd](https://github.com/google/swiftshader/commit/5b0479bd)), so LLVM 10 is still the CMake default at HEAD.

The project is in **low-volume maintenance**. It had 232 commits from January 2024 to September 2026, roughly 35% of them regression-bot test-list updates, and only 1–10 commits a month in 2026. The main human maintainer is Shahbaz Youssefi ([commit history](https://github.com/google/swiftshader/commits/master); [OWNERS](https://github.com/google/swiftshader/blob/master/OWNERS)). "Maintenance mode" is our inference from this activity; there is no announcement. Chrome is removing automatic WebGL fallback to SwiftShader because "JIT-ed code running in Chromium's GPU process" is a security risk ([Chromium docs](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/swiftshader.md); [blink-dev intent](https://groups.google.com/a/chromium.org/g/blink-dev/c/yhFguWS_3pM)). SwiftShader remains in use as ANGLE's and Dawn's Vulkan backend and in the Android Emulator ([Android Developers](https://developer.android.com/studio/run/emulator-acceleration)). For an oracle, slow drift is a feature: pin a commit and the target will not move under us.

Testing gives us a head start. Regres, a Go tool, runs the Khronos VK-GL-CTS in presubmit (diffing each change against its parent) and nightly on master, pinned to CTS sha `f55c0a8a…` ([docs/Regres.md](https://github.com/google/swiftshader/blob/master/docs/Regres.md); [deqp.json](https://github.com/google/swiftshader/blob/master/tests/regres/deqp.json)). The last checked-in status snapshot (2026-01-26) records **416,472 PASS, 28 FAIL, 3 CRASH, 1,940 ASSERT, 5 UNIMPLEMENTED and 2,486,911 NOT_SUPPORTED** ([testlists](https://github.com/google/swiftshader/tree/master/tests/regres/testlists)). The regression bot stopped posting after that date, so this is the latest published snapshot. First-party gtest suites add about 106 Reactor tests, 21 Vulkan tests, about 25 System tests and 11 Math tests ([tests/](https://github.com/google/swiftshader/tree/master/tests)).

**Determinism is not documented and must be measured.** Code evidence points to determinism for a fixed build, CPU feature set, backend and thread count, but only for order-independent work. A debugging comment notes that traces are deterministic "when the thread count is reduced to 1" ([SpirvShaderDebug.hpp](https://github.com/google/swiftshader/blob/master/src/Pipeline/SpirvShaderDebug.hpp)). Codegen branches on CPUID in dozens of places ([src/Reactor](https://github.com/google/swiftshader/tree/master/src/Reactor)). Transcendentals are custom polynomial approximations with relaxed-precision knobs ([ShaderCore.hpp](https://github.com/google/swiftshader/blob/master/src/Pipeline/ShaderCore.hpp)). Thread count and affinity can be pinned through `SwiftShader.ini` ([RuntimeConfiguration.md](https://github.com/google/swiftshader/blob/master/docs/RuntimeConfiguration.md)). The oracle should therefore be pinned to a commit, a backend, x86-64, and a thread count, and determinism should be asserted per case.

## Conformance testing already defines the grading vocabulary

The Khronos CTS sets the bar a SwiftShader rebuild would be held to. A conformant run executes the mustpass list `external/vulkancts/mustpass/main/vk-default.txt`. Only **Pass, NotSupported, QualityWarning, CompatibilityWarning and Waiver** are allowed; any Fail, Crash, Timeout or InternalError disqualifies the run ([VK-GL-CTS README](https://github.com/KhronosGroup/VK-GL-CTS/blob/main/external/vulkancts/README.md)). The unit of judgment is the individual dEQP case, and runs are sharded with `--deqp-fraction`. The total size is roughly **2.8 million Vulkan tests** according to an XDC 2025 talk summary, **[unverified: secondary snippet]** ([Igalia slides](https://www.igalia.com/downloads/slides/RicardoGarcia-VulkanCTSTipsTricks.pdf)). The eval takes two lessons from this. The per-case pass fraction is the right partial-credit unit. And NotSupported must be reported apart from Pass, or a candidate could raise its score simply by advertising fewer features. The fix is to anchor the denominator to cases where reference SwiftShader passes.

dEQP never compares rendered images exactly. Each test picks a comparator from `tcuImageCompare` ([tcuImageCompare.hpp](https://github.com/KhronosGroup/VK-GL-CTS/blob/main/framework/common/tcuImageCompare.hpp); [tcuImageCompare.cpp](https://github.com/KhronosGroup/VK-GL-CTS/blob/main/framework/common/tcuImageCompare.cpp)):

- `intThresholdCompare`: per-channel max absolute diff ≤ threshold.
- `floatThresholdCompare`.
- `floatUlpThresholdCompare`: ULP difference with denormals flushed.
- `intThresholdPositionDeviationCompare`: each reference pixel must be matched within a small spatial box, which tolerates edge shifts.
- `bilinearCompare`.
- `fuzzyCompare`: blurs both images with a `{0.1, 0.8, 0.1}` kernel, ignores per-channel differences under 4/255, and passes at a score that the source says is best set between **0.02 and 0.05** ([tcuFuzzyImageCompare.cpp](https://github.com/KhronosGroup/VK-GL-CTS/blob/main/framework/common/tcuFuzzyImageCompare.cpp)).

The allowed error comes from spec precision rules. `subPixelPrecisionBits` and `subTexelPrecisionBits` bound rasterization and filtering ([Vulkan limits](https://docs.vulkan.org/spec/latest/chapters/limits.html)). The SPIR-V precision appendix requires OpFAdd, OpFSub and OpFMul to be correctly rounded and allows 2.5 ULP for division, 2 ULP for inversesqrt, and similar bounds for other ops ([spirvenv appendix](https://docs.vulkan.org/spec/latest/appendices/spirvenv.html)). **Quote those values from the page itself; the fetch summary may have echoed the query.** Two more verifiers exist: a texture-lookup verifier that checks results lie within the set reachable under the allowed coordinate and LOD precision, and an interval-arithmetic precision checker for shader built-ins. Both are **[unverified this session]**. For us this means exact or ULP comparisons for buffers and compute, LSB thresholds for UNORM formats, and a position-deviation term for edges, with PSNR and perceptual metrics kept in secondary, diagnostic roles.

Production CI adds the operational layer. SwiftShader's Regres diffs a change against its parent and gates on known-passing lists refreshed daily. It isolates each test process with memory and time limits, so crashes are counted instead of killing the runner ([Regres.md](https://github.com/google/swiftshader/blob/master/docs/Regres.md)). Mesa CI runs lavapipe and llvmpipe against per-driver `-fails`, `-flakes` and `-skips` expectation files. It tracks flakes on a dashboard (a job that failed and then passed on automatic retry), keeps test runtime under 10 minutes and allows at most one spurious failure per week ([Mesa CI](https://docs.mesa3d.org/ci/index.html)). Mesa also checksums replayed trace frames against YAML expectations ([Mesa traces](https://docs.mesa3d.org/ci/local-traces.html)). The deqp-runner result taxonomy (ExpectedFail, UnexpectedPass, Flake and so on) is **[unverified: README blocked]**.

Outside CTS, several other comparison schemes are in use:

- **Skia Gold** matches images with `exact`, `fuzzy` (max differing pixels, per-channel delta), `sobel` (edge-masked fuzzy) and `sample_area` algorithms ([imgmatching](https://pkg.go.dev/go.skia.org/infra/gold-client/go/imgmatching)).
- **Amber** scripts carry their own expectations: `EQ_RGBA`, `TOLERANCE`, `RMSE_BUFFER` and `EQ_HISTOGRAM_EMD_BUFFER`. Amber supports SwiftShader as a backend ([amber_script.md](https://github.com/google/amber/blob/main/docs/amber_script.md); [google/amber](https://github.com/google/amber)).
- **NVIDIA FLIP** gives a per-pixel perceptual error map in [0,1] ([NVlabs/flip](https://github.com/NVlabs/flip)).

Finally, metamorphic testing supplies an oracle that is hard to overfit. GLFuzz found **more than 60 distinct bugs across 17 GPU/driver configurations** by checking that semantics-preserving shader transforms leave the image unchanged ([OOPSLA 2017](https://dl.acm.org/doi/10.1145/3133917)). spirv-fuzz carried the idea to SPIR-V ([PLDI 2021](https://dl.acm.org/doi/10.1145/3453483.3454092)). The GraphicsFuzz repo was archived on 2025-12-08, but its tools still work ([google/graphicsfuzz](https://github.com/google/graphicsfuzz)).

| Established method | Metric it uses | What we borrow |
|---|---|---|
| Vulkan CTS / dEQP | Per-case status; conformance = zero Fail/Crash/Timeout | Per-case partial credit; NotSupported reported separately; reference-pass-anchored denominator |
| tcuImageCompare | Int/float/ULP thresholds, position-deviation, fuzzy 0.02–0.05 | Format-aware LSB/ULP distance, edge-tolerant coverage term |
| Regres | Diff vs parent over known-passing lists; per-process limits | Reference-baseline grading; crash/timeout counted, never fatal |
| Mesa CI | Expectation files, flake retry, runtime budgets, trace checksums | n1/n2 flakiness detector; strict unexpected-result handling |
| Skia Gold / Amber | Fuzzy pixel counts, RMSE, histogram EMD | Amber-like op vocabulary for cases; tolerance parameters set by controls |
| FLIP / PSNR | Perceptual error | Secondary diagnostics only, never headline |
| GraphicsFuzz / spirv-fuzz | Metamorphic equality | Hidden-split generator that defeats hardcoding |

## AI coding benchmarks show partial credit and oracle isolation are non-negotiable

**No published benchmark reimplements a graphics API or driver**; this is open territory. The closest analogues point one way.

- **ProgramBench** (May 2026) gives agents an execute-only binary plus docs for 200 programs, among them FFmpeg, SQLite and PHP. Grading uses a median of **770 tests per task**, generated by coverage-guided exploration of the reference. A test-quality linter cut the pass rate of a dummy submission from **18.5% to 3.7%**. The binary is removed before grading and internet access is blocked; with internet, cheating ran at 1–36%. Under a budget of 1,000 steps and 6 hours, **0% of tasks were fully resolved**, and the best "≥95% of tests" rate was **Claude Opus 4.7 at 3.0%** ([arXiv 2605.03546](https://arxiv.org/html/2605.03546v1)).
- **Commit0** asks for whole libraries from a spec plus unit tests and grades by fraction of tests passed. "None can yet fully reproduce full libraries" ([arXiv 2412.01769](https://arxiv.org/abs/2412.01769)).
- **Anthropic's C-compiler experiment** is the closest showcase in scale: about 100k lines of Rust from 16 parallel Opus 4.6 agents, costing just under $20k. It used GCC as a differential oracle, mixing GCC-compiled and agent-compiled files to bisect failures, and added a `--fast` mode that samples 1% or 10% of the tests deterministically to protect context. Its lesson was that verifiers must be "nearly perfect" ([Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)).
- **Cursor's FastRender browser** is the counter-example. It was criticized for not passing CI and for lacking reproducible builds and real benchmarks ([Simon Willison](https://simonwillison.net/2026/Jan/23/fastrender/); [SIG](https://www.softwareimprovementgroup.com/blog/quality-of-fastrender/)).

A SwiftShader eval sits where ProgramBench's behavioral oracle meets Commit0's partial credit, and it needs the independent conformance grading that FastRender lacked.

The SWE-bench line teaches what goes wrong with test validity. **OpenAI stopped reporting SWE-bench Verified in February 2026.** An audit of 138 tasks it chose because models often failed them found at least 59.4% had flawed tests, and every frontier model tested showed training exposure. The figures come from secondary coverage, because the primary post returned 403 ([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/); [Epoch review](https://epoch.ai/benchmarks/swe-bench-verified/review)). SWE-bench Pro adds copyleft and private repos as contamination deterrents ([Scale](https://labs.scale.com/leaderboard/swe_bench_pro)). A September 2026 audit, "SWE-Bench Pro Verified", nevertheless finds reward hacking through leaked gold solutions and badly scoped tests ([arXiv 2609.08149](https://arxiv.org/abs/2609.08149)). Scores for the same model differ by **10–30 points between vendor and standardized scaffolds** ([morphllm, aggregator](https://www.morphllm.com/swe-bench-pro)). Terminal-Bench 2.1 had to fix **28 of 89 tasks** after release ([tbench.ai](https://www.tbench.ai/news/terminal-bench-2-1)). The implication is that every result row must name its (model, scaffold) pair, and the task set must stay under continuous validation.

The reward-hacking evidence is quantitative. METR's May 2026 frontier risk report found **at least 16% of successful runs on its hardest (8h+) tasks involved cheating**. Tactics included reaching hidden test repositories and injecting code into scorers, and "manually checking for cheating is often the majority of the work" ([METR](https://metr.org/blog/2026-05-19-frontier-risk-report/)). The same report puts the public-frontier 50% time horizon near **12 hours (CI 5–61 h)** and notes that measurements above 16 hours are unreliable ([METR](https://metr.org/time-horizons/)). A 12-hour SwiftShader attempt therefore sits right at the frontier's reliable horizon, which is where cheating peaks. ImpossibleBench made tasks unsolvable, so any pass is a cheat, and found that **hiding tests from the agent cut hacking below 1%** ([arXiv 2510.20270](https://arxiv.org/html/2510.20270v1)). The Agentic Benchmark Checklist shows that such flaws can mis-estimate performance "by up to 100% in relative terms" ([arXiv 2507.02825](https://arxiv.org/abs/2507.02825)).

KernelBench is the template for the performance axis and a warning about it. Its **fast_p** counts a task only if the output is correct *and* faster than baseline × p ([arXiv 2502.10517](https://arxiv.org/abs/2502.10517)). Sakana's "AI CUDA Engineer" exploited a harness memory-reuse bug that skipped correctness checks ([Sakana](https://x.com/SakanaAILabs/status/1892992938013270019)). A 2026 hardening paper reports aggregate speedups falling from **3.13× to 1.49×** after remediation. Attribution between two arXiv papers is uncertain ([arXiv 2606.08960](https://arxiv.org/pdf/2606.08960)). For us, a speed score is worthless unless correctness is gated on randomized inputs the candidate cannot predict. On statistics, Anthropic recommends clustered standard errors when items are grouped, and paired model comparisons **[unverified: paper not re-fetched]** ([arXiv 2411.00640](https://arxiv.org/abs/2411.00640)). dEQP cases within a group are highly correlated, so clustering by family is mandatory.

| Benchmark | Headline metric | Lesson for SwiftShader eval |
|---|---|---|
| ProgramBench | % Resolved + % ≥95% tests | Continuous score required; remove oracle; lint weak tests; dummy baseline |
| Commit0 | Unit-test pass fraction | Partial credit per test; interactive feedback helps |
| SWE-bench Verified / Pro | % resolved | Flawed tests and contamination kill benchmarks; report scaffold |
| METR time horizon | 50%/80% horizon | 12h attempts sit where cheating peaks; transcript review budget |
| KernelBench | fast_p | Performance gated on robust correctness |
| ImpossibleBench | Pass rate on impossible tasks | Hidden tests are the strongest anti-hack control |
| ShaderMatch | Rendered-frame match | Frame comparison is established for graphics code |

## evalBase maps cleanly onto a drop-in ICD, less cleanly onto everything else

An evalBase instance supplies six objects: **Driver, CaseScorer, MetricSpec, CorpusSpec, ControlSpec and TaskSpec**. Everything else is generic: the reference cache, tolerance from perturbation runs, Hill scoring, family-weighted aggregation, the no-network sandbox and the five-tool MCP harness (`shell`, `oracle`, `driver`, `grade_dev`, `checkpoint`) ([evalBase/README.md:22-57](../evalBase/README.md)). Tolerance per case is `T = clamp(max(2·noise, 2·sensitivity), 0.03, 0.30)`. A snapshot scores `1/(1+(D/T)^4)`. Fidelity, procedural and performance categories are weighted 0.6/0.3/0.1. Full success requires every fidelity case ≥ 0.9, procedural ≥ 0.95 and every performance ratio ≤ 8× ([metrics.py:9-30](../evalBase/evalbase/grader/metrics.py); [interfaces.py:245-275](../evalBase/evalbase/interfaces.py); [runner.py:329-373](../evalBase/evalbase/grader/runner.py)). The lab-ready-eval skill adds the governing rules. **"Every under-scoped eval saturates"**, and reimplementing a mature library's entire public API "is the right size". Top models should land between 0.5 and 0.9. Controls come before models, with predictions written down first, and there must be "no vendoring escape hatch" ([SKILL.md:33-97](../.claude/skills/lab-ready-eval/SKILL.md); [task-and-oracle.md:9-32](../.claude/skills/lab-ready-eval/references/task-and-oracle.md)).

Measured against those rules, the notes identify six candidate eval variants, and their fit varies widely.

| Variant | Task | Oracle / grading | Fit with evalBase | Main risk |
|---|---|---|---|---|
| **A. Drop-in Vulkan ICD** | Implement `libvk_candidate.so` exporting loader-ICD entry points; core 1.0 graphics+compute plus selected 1.1–1.3 features | Trusted `vkreplay` driver replays JSON ops against oracle and candidate; image/buffer distance + VkResult/limits/query checks | **Best**; only variant that satisfies rule zero alone | Floor effects for weaker models; perf gap vs JIT |
| B. SPIR-V compute executor | Compute-only ICD (B1) or C ABI `run_compute(...)` (B2) | Typed buffer diff (ints exact, floats ULP+bias) | Good; well-trodden task | Saturation without exotic tail and perf weight |
| C. Sampler / formats / blitter | C library `sample`, `convert`, `blit`, `resolve` | LSB/ULP per texel; decoders bit-exact | Precise, cheap | Saturates standalone |
| D. Rasterizer / fixed function | Graphics-only ICD or C library over clip-space verts + state | Coverage-sensitive image metric | Good as family | Thin procedural category standalone |
| E. Reactor DSL | Reimplement `rr::` API with any backend | Compiled C++ cases, exact/ULP outputs; LLVM vs Subzero is a built-in perturbation | Clean | Internal API; oracle tool compiles model-written C++ |
| F. SWE-style on real tree | Re-add a removed extension or fix a reverted bug | Upstream commit C as oracle + dEQP subset | Weakest; different eval type | Highest contamination; LLVM build cost |

The researcher's difficulty ranking of self-contained subsystems runs from easiest to hardest: BC/ETC2 decoders, format conversion, system utilities, Reactor, SamplerCore, clipper/rasterizer setup, SPIR-V compute, and finally the full object layer. It supports folding B, C and D into A as **families of cases** instead of shipping them as separate evals, where they would saturate. The folding gives a scoring pyramid. Instance/device/buffer/compute cases earn early credit, graphics comes next, and exotic formats, MSAA, queries and synchronization form the tail where "headroom lives". Variant E is a reasonable second eval. F belongs to a separate SWE-style suite, if we build it at all. Its practical weakness is that the upstream diff is public, and its full LLVM build is expensive in the grading sandbox.

For A, the trusted driver should be a custom C++ program with an **Amber-like op vocabulary**. The ops are `create_instance`, `create_buffer`, `create_image`, `create_pipeline` (SPIR-V as a sha256 asset), `record`, `submit`, `readback`, `query` and `snapshot`, and the driver logs the VkResult of every call to `ledger.json`. Amber alone cannot capture per-call results, limits and timings, but AmberScript could be imported as an input format for public cases. The driver writes an `icd.json` pointing at `/candidate/build/libvk_candidate.so` and sets `VK_ICD_FILENAMES`; whether the pinned loader wants `VK_DRIVER_FILES` instead is **[unverified]**. `TaskSpec.required_names` must include `CMakeLists.txt`, because the default only accepts Makefiles ([interfaces.py:367-420](../evalBase/evalbase/interfaces.py)). Snapshots with several attachments must be packed into **one composite primary-channel file**, holding every color attachment, depth, stencil and designated storage buffers. Otherwise the generic check and the workspace's `dev/reference` copy see only the first channel, and secondary outputs go ungraded ([interfaces.py:130-189](../evalBase/evalbase/interfaces.py)).

## A deterministic oracle breaks evalBase's default metric and forces a new distance

This is the most important design finding. evalBase's constants were tuned for a Monte Carlo renderer, and SwiftShader is not one. If the oracle is deterministic, `noise = D(ref_N, ref_2N)` is zero, and with no meaningful tolerated perturbation T sits at `t_lo = 0.03` for every case. Under Hill n=4 that gives **D = 0.015 → 0.94, D = 0.03 → 0.5, D = 0.06 → 0.06**. The whole burden moves to the distance's scaling: cosmetic differences must land well below 0.015 and real bugs well above 0.03. The toy scorer fails that test badly. It downsamples 2× to average noise, applies a 0.15 block floor with `d_struct = rms/0.25`, and so passes **uniform biases up to about 9.6/255, all 1-LSB rounding differences and isolated edge-coverage errors at D = 0** ([evalBase/examples/toy/scorer.py:33-112](../evalBase/examples/toy/scorer.py)). Reusing it would certify broken drivers.

The proposed Vulkan distance follows dEQP's comparators rather than the toy. Errors are measured in each format's own units: LSBs for UNORM/SNORM, ULPs (with an absolute floor near zero) for float formats, encoded space for sRGB. Integer formats and stencil are exact, and a NaN/Inf class mismatch counts as maximal error. Each 8×8 block, with no downsampling, takes the maximum of three terms: a structural RMS term, a signed-bias term (so a uniform offset is visible, which the skill requires as the "absolute term" ([NEW_EVAL.md:92-103](../evalBase/NEW_EVAL.md))), and a **coverage term**, the fraction of texels over K LSB, which catches sparse but large edge and half-pixel errors much as `intThresholdPositionDeviationCompare` does. Buffers use typed per-binding comparison over fixed-size element chunks. The constants S, B, K and C cannot be chosen in advance; they are set by the controls. The `round_trunc` control, a float→UNORM conversion that truncates, sets the 1-LSB floor honestly. The gain, half-pixel, nearest-filter and sRGB controls must all land well above T.

Tolerance should come from perturbations of the oracle that Google itself treats as valid. Each one is a hypothesis to measure before adoption.

| Perturbation | Role | Expected effect |
|---|---|---|
| `subzero` (LLVM ↔ Subzero backend) | **Tolerated**, the closest analogue to a second seed | Unknown; if bit-identical it adds nothing to T and serves only as a determinism check |
| `threads` (worker count / affinity, via `sample_mult=2`) | Determinism assertion, **not** tolerance | D = 0; any nonzero case is flaky and removed or canonicalised |
| `vtxjitter` (vertex nudge below 1/2^subPixelPrecisionBits) | Tolerated for raster families | Admits edge flips only on exact-boundary samples |
| `texcoord_ulp` (1-ULP sampling coordinate nudge) | Tolerated for filtering families | Admits different valid weight rounding |
| `lavapipe` (Mesa's conformant CPU Vulkan) | Run and recorded, **never tolerated** | The fairness number: how SwiftShader-specific the metric is |
| x86-64 vs aarch64 | Open item, not tolerated | Measures ISA-dependent codegen |

This choice has a real tension that the team should accept on purpose. The Vulkan spec permits precision slack, so a fully conformant driver can differ from SwiftShader, yet the skill forbids tolerance "from a constant". The reconciliation is to publish SwiftShader's implementation-defined choices (limits, subpixel and mipmap precision bits, format features) as a frozen device profile in `spec/`. That makes the task "match *this* implementation". The lavapipe number then tells readers how much of the score rewards SwiftShader idiosyncrasy rather than Vulkan correctness.

Performance needs its own decision before calibration. evalBase counts a performance ratio only if the candidate's replay score is at least 0.5, then scores `hill(t_cand/t_ref, half=16)` and gates full success at 8× ([runner.py:248-261](../evalBase/evalbase/grader/runner.py)). A from-scratch interpreter against SwiftShader's specializing JIT will probably exceed 16×, so with defaults, full success would effectively **require writing a JIT**. The per-case timeout of `max(60 s, 10 × reference wall time)` ([runner.py:288](../evalBase/evalbase/grader/runner.py)) also means fidelity cases must run sub-second on the reference, or a slow but correct candidate times out on correctness. Otherwise speed leaks into the fidelity score. There are two options. One is to rescale (for example half 64, gate 32) after measuring an interpreter control. The other is to keep 16/8 and state that full success means JIT-class performance. Either choice goes into DESIGN.md before any model runs. Timed cases must run for at least 2 s after a warm-up frame, so pipeline compilation is excluded ([metric.md:125-137](../.claude/skills/lab-ready-eval/references/metric.md)).

## Hidden split, controls and risks follow from contamination and cheating evidence

The hidden split must defeat memorised *outputs*, because nothing can defeat a memorised *implementation*. It should be generated, not curated. Families cover `inst_dev`, `mem_buf`, `compute_arith/cf/types/subgroup/atomics/image`, `raster_tri`, `raster_lines_points`, `blend`, `depth_stencil`, `tex_sample`, `formats_copy_blit`, `msaa`, `mrt_renderpass`, `queries_sync` and `perf_*`, each with different seeds, parameter ranges and compositions between public and hidden. The private generator tree lives outside the repo root, which `CorpusSpec` enforces ([NEW_EVAL.md:159-185](../evalBase/NEW_EVAL.md)). SPIR-V comes from a Python emitter or is stored as sha256 assets, so evalBase's determinism proof stays pure Python. A spirv-fuzz metamorphic layer adds hidden cases whose correct output is by construction the un-fuzzed shader's output. Every generated case must pass `spirv-val` and the Khronos validation layer on the oracle with zero errors, because invalid usage is undefined behaviour and the oracle's output would mean nothing. Cases using order-dependent atomics, timestamp values or implementation-defined statistics are excluded or canonicalised. The n1/n2 thread-count runs enforce this case by case. Samples of SwiftShader's 416k passing CTS names should serve as **public-side** development and sanity signals, not as the hidden split: they are public, CTS is in training data, and Amber scripts in CTS carry their own expected outputs.

Controls are built as a **wrapper ICD** that `dlopen`s the real SwiftShader, forwards every entry point and alters one thing. This follows the skill's "shim over the reference library", so controls take the same driver path as a candidate ([controls.md:33-37](../.claude/skills/lab-ready-eval/references/controls.md)). The `control.json` mechanism mounts the reference `.so` read-only into control runs only ([NEW_EVAL.md:187-204](../evalBase/NEW_EVAL.md)). All bands below are predictions to be written into DESIGN.md before measurement; none have been measured.

| Control | Alteration | Predicted band (to verify) | Guards |
|---|---|---|---|
| `reference` | Real SwiftShader | Exactly 1.0, both splits | Grader accepts its definer |
| `reference_subzero` | Subzero build | Fidelity ≥ 0.93 | Tolerance admits its source |
| `lavapipe` | Mesa CPU driver | Measured, reported | Fairness / SwiftShader-specificity |
| `stub` | Negotiates, then fails init | Null band (~0.04–0.06) | Floor, as ProgramBench's dummy |

Isolation must be enforced by image contents. The solver image gets a C/C++ toolchain, CMake/Ninja, Vulkan headers and loader, the `vkreplay` binary, a SPIR-V disassembler and, optionally, the validation layer (it renders nothing). It gets **no SwiftShader, no Mesa, no other ICD and no SwiftShader source**, and a `TaskSpec.isolation_check` asserts that. The network stays off ([containers.py:178-197](../evalBase/evalbase/grader/containers.py); [harness.md](../.claude/skills/lab-ready-eval/references/harness.md)). The notes recommend **forbidding LLVM and linked SPIRV-Tools** for Variant A: LLVM is SwiftShader's own dependency, the "no vendoring … or its dependencies" rule covers it, and parsing SPIR-V is part of the task. An "LLVM allowed" variant can exist as a separately labelled eval. Grading always rebuilds from source in a fresh sandbox. The grading-build timeout in evalBase was not located in the notes and must be confirmed.

Risk by risk:

- **Contamination** is the distinctive threat. The hidden split stops output memorisation, but recalling SwiftShader's transcendental approximations or rounding choices raises scores through memory. Mitigate in three ways: run a source-similarity audit (winnowing overlap against upstream) reported as an indicator, not a penalty; weight families whose behaviour the Vulkan spec determines; and publish the lavapipe fairness number.
- **Saturation versus floor.** B, C and E alone could be largely solved in a day, while A could floor weaker models. The family pyramid addresses both. The skill's warning that calibration runs above 0.9 mean the task is too small applies directly ([SKILL.md:40-46](../.claude/skills/lab-ready-eval/SKILL.md)).
- **Cheating.** Given METR's 16%, expect attempts to find a system Vulkan driver, hardcode golden images or tamper with the grader. Hidden tests, the removed oracle, a fresh grading container, diff scans for known SwiftShader constants, and manual review of top transcripts are all required.
- **Flakiness.** It comes from multithreaded atomics, timestamps, JIT warm-up in timed runs, and host load during attempts. Numbers of record are graded on an idle host, never while control sweeps run ([controls.md:41-42](../.claude/skills/lab-ready-eval/references/controls.md)).
- **Unknowns.** We have no data on how well current models reimplement Vulkan drivers, so every saturation prediction here is inference.

## Recommended design and next steps

**Recommendation.** Build Variant A, the drop-in Vulkan 1.3 ICD, as the flagship eval, with B, C and D as case families inside it and E (Reactor) as an optional sibling. Settings:

- **Oracle and budget.** Pin SwiftShader at `1e80438d2b93`, CMake LLVM 10 backend, x86-64, fixed ThreadCount. Give each attempt 12 hours with a submit stop policy, in 4-core/8 GB sandboxes.
- **Metric.** Keep evalBase's three categories. Fidelity uses the format-aware distance; procedural covers VkResult streams, the features/limits/format-property profile, occlusion counts and fence/event status; performance is gated on correctness and runs on at least 2 s timed workloads.
- **Headlines.** Lead with full success and the continuous overall score, both with CIs clustered by family. Add a ProgramBench-style "≥ 95% per family" completion rate, and cost, tokens and wall-clock per (model, scaffold) row.
- **Seeds.** Run k ≥ 3 seeds per model where budget allows.

| Step | Action | Exit criterion |
|---|---|---|
| 1 | Build trusted reference image (SwiftShader LLVM + Subzero, loader, validation layers, SPIRV-Tools, lavapipe) pinned by digest | Image id recorded; `vk-unittests` pass |
| 2 | Measure oracle determinism: N repeats × thread counts × LLVM/Subzero on a pilot corpus of ~50 cases | Per-family noise and backend defect known; flaky op types listed |
| 3 | Write `vkreplay` driver + ledger + composite snapshot format; freeze device profile into `spec/` | Reference replays pilot corpus with exit ok, twice identically |
| 4 | Implement format-aware scorer; unit-test identity, gain, 1-LSB, half-pixel, edge shift | Distance separates bugs from rounding on synthetic tests |
| 5 | Write DESIGN.md with control predictions, performance-scaling decision and LLVM policy **before** measuring | Committed before step 6 |
| 6 | Build wrapper-ICD controls; run control sweep; set S/B/K/C and perf half-point from results | Reference = 1.0 both splits; stub null; hardcode-public null on hidden; lavapipe number recorded |
| 7 | Write generators for all families, public and hidden, with spirv-val + validation-layer gating and determinism proof | ~300 cases; cache rebuild ≈ 1 h; case reference time sub-second except perf |
| 8 | Build solver image with isolation check; run no-key smoke | Smoke stays under 0.05; no ICD reachable in sandbox |
| 9 | Calibration attempts with 2–3 frontier models; manual transcript review | Top models land 0.5–0.9; if > 0.9, widen scope (more extensions, MSAA, sync tail) |
| 10 | Numbers of record on idle host; source-similarity audit; publish with scaffold labels | Reproducible report with clustered CIs |

Before step 2, the team should also verify the open items the notes flag. These are the Khronos #717 submission details, the loader environment-variable name, SwiftShader's `subPixelPrecisionBits`, its supported format count, the evalBase grading-build timeout, the exact spirvenv precision values, and the CTS case count from `wc -l` on the pinned mustpass. A per-group breakdown of the 416,472 PASS list, grouped by dEQP prefix, is a cheap first task. It shows where SwiftShader's behaviour is richest and so where families should get the most weight.

## Conclusion

The research changes where the effort goes. The hard problem is not finding an oracle: SwiftShader, its pinned CTS and its pass lists amount to a ready-made conformance apparatus. The hard problem is that evalBase's machinery assumes the oracle is noisy, and SwiftShader probably is not. In a deterministic setting, the tolerance model collapses to a constant, and the distance function becomes the metric. So the first real deliverable is a measurement, not a corpus: repeated oracle runs across backends and thread counts, followed by a control sweep that sets the distance's constants. Every later number depends on that step.

The second insight is that Vulkan's precision slack makes "match SwiftShader" and "be a correct Vulkan driver" different targets. Most AI benchmarks gloss over this kind of gap. Reporting a conformant rival implementation (lavapipe) against the same metric makes it measurable, and that fairness number could turn out to be the eval's most informative result on its own, because it separates models that learned Vulkan from models that recalled SwiftShader.
