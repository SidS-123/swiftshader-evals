# Mapping evalBase and the lab-ready-eval skill onto SwiftShader evals

Scope: how the local evalBase framework (`evalBase/`) and the `lab-ready-eval` skill (`.claude/skills/lab-ready-eval/`) would be applied to build evals of coding models on Google SwiftShader, and which concrete eval designs follow. ## Q1. What exactly does an evalBase instance supply, and what does the generic machinery do with it? (extension points, ledger, T and Hill scoring, categories, bars, controls, harness, skill rules)

### Takeaway
An instance is one `Instance` value that supplies six objects (Driver, CaseScorer, MetricSpec, CorpusSpec, ControlSpec, TaskSpec); everything else (reference cache, per-case tolerance from perturbation runs, Hill scoring, family-weighted aggregation, regrade, sandbox, 5-tool MCP harness, smoke, reports) is generic. A SwiftShader eval therefore reduces to: a trusted Vulkan driver program honouring the ledger contract, a Vulkan-aware distance, ledger checks, generators, control shims, and task text. The default constants (k=2, T in [0.03, 0.30], Hill n=4, weights 0.6/0.3/0.1, bars 0.9/0.95/8x) were tuned for a *noisy* renderer and need rethinking for a *deterministic* oracle like SwiftShader.

### Inferences
- **Deterministic oracle consequence.** SwiftShader is not Monte Carlo: `D(ref_N, ref_2N)` will be 0 on (almost) every case, so T = max(t_lo, 2·sensitivity). With no meaningful tolerated perturbation, T sits at t_lo = 0.03 everywhere, and scores are then: D=0.015 → 0.94, D=0.03 → 0.5, D=0.06 → 0.06. The whole design burden moves to (a) the distance's scaling (cosmetic differences must land ≪ 0.015, real bugs ≫ 0.03) and (b) choosing SwiftShader-meaningful perturbations (Q3).
- The n1/n2 pair can be repurposed as a **flakiness detector**: have the driver map `sample_mult=2` to "re-run with a different worker-thread count / CPU affinity". Any case with noise > 0 exposes oracle nondeterminism (atomics ordering, timestamp queries) and should be removed or its output canonicalised — rather than letting it widen T.
- Because `generic_checks` only uses `load_output` with the default (primary) channel and the workspace only copies `primary_channel` outputs to `dev/reference` (interfaces.py:147-148), a multi-attachment Vulkan snapshot should be packed as one composite primary-channel file (e.g., one `.npz`/KTX2-like container per snapshot holding all color attachments, depth, stencil, and bound storage buffers), with `load_output` returning a dict and `distance` combining per-attachment defects (max or weighted). Otherwise secondary attachments are ungraded and invisible to the model.
- `required_names` defaults to Makefile variants (interfaces.py:402); a CMake/Ninja C++ candidate needs `required_names={"CMakeLists.txt","Makefile"}` or the export is refused.
- The 10× reference-time timeout (runner.py:288) with a 60 s floor matters: an interpreter-style candidate that is 50–200x slower than SwiftShader's JIT would time out on any fidelity case whose reference takes > ~0.3–1 s. Keep fidelity cases sub-second on the reference so correctness and speed are measured separately.

## Q2. Candidate SwiftShader eval tasks at different scopes: case format, driver, distance, procedural checks, performance, perturbations, controls, hidden split

### Takeaway
Six variants map onto evalBase with very different fit. **A (drop-in Vulkan ICD)** is the natural "reimplement the public API" shape the skill was distilled from, and the only one that satisfies rule zero on its own; B (SPIR-V compute executor), C (sampler/format/blitter) and D (rasterizer) are best used as families *inside* A's corpus (or as smaller sibling evals with an exotic tail), E (Reactor) is a clean library-reimplementation eval with a built-in perturbation (LLVM vs Subzero), and F (SWE-style on the real tree) fits evalBase awkwardly and is most exposed to contamination.

### Cited Findings (SwiftShader / ecosystem facts used)
- SwiftShader is "a high-performance CPU-based implementation of the Vulkan 1.3 graphics API", Apache 2.0, CMake build; used as an ICD by renaming to `vulkan-1.dll`/`.so` or setting `VK_ICD_FILENAMES` to the path of `vk_swiftshader_icd.json`; tested with dEQP; bundles Subzero and a minimized LLVM ("LLVM-Subzero") — [google/swiftshader README](https://github.com/google/swiftshader)
- `set(DEFAULT_REACTOR_BACKEND "LLVM")`, `REACTOR_BACKEND` cache string "JIT compiler back-end used by Reactor"; `DEFAULT_SWIFTSHADER_LLVM_VERSION "10.0"`; `SWIFTSHADER_ENABLE_ASTC` default TRUE; no fast-math/precision option in the top-level CMakeLists — [swiftshader CMakeLists.txt](https://raw.githubusercontent.com/google/swiftshader/master/CMakeLists.txt)
- "Reactor is an embedded language for C++ to facilitate dynamic code generation and specialization", uses operator overloading (capitalised types like `Float`) with plain C++ `if` deciding what ends up in the generated routine — [SwiftShader docs/Reactor.md](https://github.com/google/swiftshader/blob/master/docs/Reactor.md)
- Amber is "a multi-API shader test framework"; AmberScript (preferred) and legacy VkScript; scripts define buffers, images, shaders (SPIR-V hex, SPIR-V assembly, or higher-level languages), graphics pipelines with attachments, EXPECT directives, and output files for result buffers/images; runs against any Vulkan implementation; SwiftShader explicitly supported via `AMBER_ENABLE_SWIFTSHADER`; Apache-2.0 — [google/amber](https://github.com/google/amber)
- Chrome deprecated automatic SwiftShader WebGL fallback (DevTools notice since Chrome 130, phased opt-in from Chrome 139) because "SwiftShader is a high security risk due to JIT-ed code running in Chromium's GPU process"; still usable via `--enable-unsafe-swiftshader` — [Intent to Remove / chromestatus summary via search](https://chromestatus.com/feature/5166674414927872), [blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/yhFguWS_3pM)
- Skill: numeric-array tolerance can come from "a different but valid summation order" — [task-and-oracle.md:87-91](.claude/skills/lab-ready-eval/references/task-and-oracle.md); text/structured-log canonicalisation for event streams — [task-and-oracle.md:96-99](.claude/skills/lab-ready-eval/references/task-and-oracle.md)

### Inferences — the variants

Common trusted pieces for A–D: a **reference image** holding pinned SwiftShader (built twice: `REACTOR_BACKEND=LLVM` and `=Subzero`), the Khronos Vulkan loader, the trusted driver binary (`vkreplay`), glslang/SPIRV-Tools for case generation/validation, the Khronos validation layer (generator-side only), and optionally Mesa lavapipe as a second conformant CPU implementation for fairness measurement. The **solver image** holds the C/C++ toolchain, CMake/Ninja, Vulkan headers, the loader, and the same `vkreplay` binary (because `driver_command` runs in the sandbox), and nothing that implements Vulkan.

#### A. Full Vulkan ICD reimplementation (drop-in `libvk_swiftshader` replacement)
- **Artifact / build**: `build/libvk_candidate.so` (+ `icd.json` written by the driver); `build_command="cmake -S /task -B /task/build -G Ninja && ninja -C /task/build"`; `required_names={"CMakeLists.txt"}`.
- **Driver**: a trusted C++ program (`vkreplay case.json outdir assets --icd <so>`) that points the loader at the candidate (`VK_ICD_FILENAMES`) or `dlopen`s it and calls `vk_icdGetInstanceProcAddr` directly (fewer moving parts, but forces the candidate to implement the loader-ICD negotiation, which is part of the "drop-in" contract anyway). It executes JSON ops (`create_instance`, `enumerate_devices`, `create_buffer`, `create_image`, `create_pipeline {spirv asset, state}`, `record`, `submit`, `wait`, `readback`, `query`, `snapshot`) and writes ledger events per call with the `VkResult`. An alternative is to reuse Amber as the executor: AmberScript already expresses buffers/images/pipelines and dumps result buffers/images; but a custom driver is needed anyway for per-call VkResult capture, queries, features/limits, timing and the ledger — recommendation: custom driver with an Amber-like op vocabulary, optionally importing AmberScript as an input format for public cases.
- **Case format**: `{"name","family","category","meta":{"timed_run_index"},"assets":{spirv/texture blobs by sha256},"ops":[...]}`; sequences of frames with mutations (update uniform/descriptor, re-record command buffer, resize attachment, reset query pool, re-submit after `VK_NOT_READY`), snapshot after each.
- **Distance**: per-attachment Vulkan image metric (Q3) + buffer metric for SSBO outputs.
- **Procedural checks** (all from reference ledger): per-call VkResult stream equality (collapsed like toy `error_codes`); `vkGetPhysicalDeviceFeatures2/Properties2/Limits` equality against a frozen SwiftShader device profile published in `spec/`; `vkGetPhysicalDeviceFormatProperties` / `ImageFormatProperties` (incl. `VK_ERROR_FORMAT_NOT_SUPPORTED`); memory type/heap layout; occlusion query exact counts; `vkGetQueryPoolResults` availability bits and `VK_NOT_READY` without WAIT; fence/event status (`VK_NOT_READY`/`VK_SUCCESS`, `VK_EVENT_SET/RESET`); `vkGetImageSubresourceLayout` for linear images (implementation-defined → from profile); timestamps checked only for validity/monotonicity, never value. Invalid-usage cases must never be generated (VUID violations are undefined behaviour; the oracle output would be meaningless).
- **Performance**: ≥2 s reference timed runs (skill rule): high-res fill-rate scene with many draws, heavy fragment shading, trilinear/anisotropic texture-heavy pass, large compute dispatch (e.g., matmul), MSAA resolve; `timed_run_index` points after a warm-up frame so JIT pipeline compile is excluded, plus one separate "pipeline creation" perf case if compile speed is to count.
- **Perturbations**: see Q3; candidates: `subzero` (backend swap, tolerated), `threads1`/`threadsN` (affinity, expected identical, acts as determinism check), `vtxjitter` (sub-subpixel vertex nudge, tolerated for edge-coverage flips), `lavapipe` (run but NOT tolerated: recorded fairness number for "a different conformant implementation").
- **Controls**: built as a *wrapper ICD* over the real SwiftShader (dlopen `libvk_swiftshader.so`, forward every entry point, alter one thing) = the skill's "shim over the reference library"; or as one-line patched SwiftShader builds in the trusted image. List in Q2 table below.
- **Hidden split**: families below; hidden draws differ in seeds, parameter ranges and compositions.
- **Fit**: best. Over-scoped per rule zero (core Vulkan 1.0 graphics+compute plus selected 1.1–1.3 features in 12 h). Score is a continuum: instance/device/buffer/compute cases give early credit, graphics next, exotic formats/MSAA/queries/sync as tail.

#### B. SPIR-V → CPU compute executor only
- **Two framings**: (B1) a compute-only Vulkan ICD (same driver as A, only compute families; forward-compatible with A); (B2) a C ABI library `int run_compute(const uint32_t* spirv, size_t n, const Binding* b, int nb, const void* push, uint32_t gx, gy, gz)` driven by a trusted harness binary, with the oracle being the same op executed through SwiftShader's Vulkan compute path. B1 keeps the drop-in property; B2 isolates shader semantics.
- **Distance**: typed buffer comparison declared in the case (layout per binding): integers/bools exact (D = fraction of mismatching elements, scaled so one wrong lane in a small buffer is ≫ T); floats as ULP distance mapped through a floor (e.g., ≤ N ULP → 0) and a bias term (mean signed error) so a systematic rounding-mode error is visible; NaN/Inf class must match exactly.
- **Procedural**: pipeline creation VkResult, specialization-constant behaviour, workgroup-size limits from profile, `OpControlBarrier` correctness observed through outputs.
- **Perturbations**: `subzero` vs `llvm` backend (captures legitimate codegen variation in transcendentals/FMA contraction, if any); "valid summation order" style reordering is not applicable to a deterministic executor except for atomics-based reductions (canonicalise or avoid).
- **Hidden split generators**: random structured SPIR-V programs from a Python SPIR-V emitter (arithmetic over int8/16/32/64, float16/32/64, vector/matrix ops, control flow with OpPhi/loops/switch/`OpKill`-free compute, subgroup ops, atomics with order-independent results, image load/store, shared memory + barriers, `SignedZeroInfNanPreserve`/`RoundingModeRTE/RTZ`/denorm float-controls). GraphicsFuzz-style metamorphic cases via spirv-fuzz on seed shaders (semantics-preserving transforms: output must equal the un-fuzzed output). All generated modules gated by `spirv-val` and by running cleanly on the oracle with validation layers.
- **Fit**: good, but under-scoped on its own (SPIR-V interpreters are a well-trodden task); needs the exotic tail and a performance category that rewards JIT/vectorisation to avoid saturation.

#### C. Texture sampler + format conversion + blitter
- **API**: C library (`sample(image_desc, sampler_desc, coords[], lod/bias/grad) -> texels`, `convert(src_fmt, dst_fmt, data)`, `blit(src, dst, regions, filter)`, `resolve(msaa)`), oracle = SwiftShader executing an equivalent compute/fragment shader that samples at the given coordinates and writes a float/uint buffer, or `vkCmdBlitImage`/`vkCmdCopy*`/`vkCmdResolveImage`.
- **Distance**: per-texel error in units of the destination format's LSB (UNORM/SNORM), ULP for float formats, exact for UINT/SINT and for stencil; bias term per block; compressed formats (BC/ETC2/ASTC — ASTC enabled by default in SwiftShader's build) as decode-to-RGBA then compare in LSB.
- **Procedural**: format feature support matrix (`VK_FORMAT_FEATURE_*`) vs profile; `VK_ERROR_FORMAT_NOT_SUPPORTED`.
- **Generators**: formats × filters (nearest/linear/cubic if exposed) × mipmap mode × address modes (repeat, mirrored, clamp-to-edge, clamp-to-border with each border colour incl. custom) × unnormalized coords × anisotropy × LOD clamp/bias × compare ops (depth compare / PCF) × gather × array layers/cube faces (seamless cube edges) × sRGB decode; coordinates biased toward texel boundaries and half-texel positions where rounding differences live.
- **Fit**: very precise oracle, cheap cases, but smaller surface; best as a family group in A. As standalone it will likely saturate unless it covers every Vulkan format (SwiftShader supports a large set; exact count is a gap).

#### D. Rasterizer / fixed-function pipeline
- **API**: either A's ICD restricted to graphics with passthrough shaders, or a C library taking post-VS clip-space vertices + state (viewport/scissor, cull/front-face, polygon mode, depth bias/clamp, depth/stencil ops, blend equations/factors/constants/logic ops, color write masks, sample count/mask, alpha-to-coverage, line width/points) and returning attachments.
- **Distance**: coverage-sensitive image metric (Q3): exact per-sample coverage is well defined by Vulkan's top-left rule and SwiftShader's subpixel precision, so edges should match exactly unless the candidate uses different fixed-point precision.
- **Perturbations**: `vtxjitter` (vertex positions nudged by < 1/2^subPixelPrecisionBits of a pixel: tolerated edge flips only where a vertex/edge lies exactly on a sample) — this is the Vulkan analog of the toy's 1/256 camera `jitter` ([examples/toy/docs/DESIGN.md:44-45](evalBase/examples/toy/docs/DESIGN.md)).
- **Generators**: random triangle soups including shared edges/T-junctions (watertightness), degenerate/sliver triangles, huge triangles needing guard-band clipping, near/far plane clipping with depthClamp, points/lines (Bresenham vs rectangular lines if `VK_EXT_line_rasterization`), blend matrix (every factor × every op × formats incl. sRGB and integer attachments with logic ops), depth/stencil matrix (compare ops × stencil ops × masks × reference values × D16/D24S8/D32/D32S8), MSAA 1/4 samples (sample shading, sample mask, resolve), multiple render targets with different formats, dynamic state.
- **Fit**: good as a family group of A. As a standalone C-library task it loses the Vulkan API surface (and the procedural category becomes thin).

#### E. Reactor JIT DSL reimplementation
- **API**: reimplement Reactor's public C++ API (`rr::Function<...>`, `Int/Int4/Float4/Pointer`, arithmetic, comparisons, `If/While/For`, `Call`, coroutines if graded) with any backend (own x86-64 code emitter, or LLVM if allowed). Oracle = upstream Reactor.
- **Driver**: cases are generated C++ translation units that build a routine with Reactor and call it on inputs; the trusted driver compiles them against the candidate's headers/library at run time (so `driver_command` includes a compile step), writes outputs as typed buffers.
- **Distance**: exact for integer/bitwise ops, ULP-with-floor for float ops.
- **Perturbations**: `subzero` vs `llvm` — the most natural perturbation of all six variants, because it is literally two conforming backends of the same API; plus `-O0` vs default optimisation level if Reactor exposes it (gap).
- **Fit**: clean, but Reactor's API is SwiftShader-internal (not a public, stable API) and the case language is C++ source, which makes `inspect_case` and the `oracle` tool riskier (compiling model-written C++ in the trusted image). Medium scope; saturation risk unless performance weight is significant.

#### F. SWE-style tasks on the real SwiftShader codebase (implement a missing extension / fix a bug)
- **Shape**: the workspace is SwiftShader at commit C−1 with an extension or feature removed (or a historical commit that added `VK_EXT_*` reverted); the model must re-implement it. Oracle = upstream SwiftShader at commit C (or a later build where the feature exists). Cases exercise the extension; grading can reuse A's driver, distance and checks unchanged; an extra category could be a dEQP-VK subset pass rate derived from the reference's own results (tests that pass on the reference must pass; `NotSupported` must match) — evalBase allows extra categories gated by `case_bar` ([NEW_EVAL.md:147-152](evalBase/NEW_EVAL.md)).
- **Practicalities**: artifact is the rebuilt `libvk_swiftshader.so`; full clean build in the grading sandbox is expensive (LLVM 10 is bundled per CMakeLists) — could ship a pre-built build directory in the starter so only incremental builds are needed; regressions matter, so every case family of A should also be in the corpus as a regression guard.
- **Fit**: weakest for evalBase's "reimplement from scratch against an oracle" philosophy; highest contamination (the upstream commit is public and likely in training data); scope per task is small (hours), so it would be a suite of many small tasks rather than one day-long task. Consider it a separate eval type.

## Q3. Where the toy's image scorer fits and what must change for Vulkan outputs; which perturbations define tolerance

### Takeaway
The toy scorer's shape (block metric with a floor, a structural term and an absolute luminance term, degenerate-output override) is the right skeleton, but its constants were chosen to absorb Monte Carlo noise and would hide real Vulkan bugs: with the toy constants a uniform bias of up to ~9 LSB in an 8-bit channel is invisible. A SwiftShader scorer needs format-aware, LSB/ULP-scaled errors without downsampling, a coverage/edge term, exact comparison for integer and stencil data, NaN-class matching, multi-attachment composite snapshots, and typed-buffer distances.

### Cited Findings
- Toy scorer: 8-bit PGM, 2x box downsample ("per-pixel Monte Carlo noise averages out"), 8x8 blocks, `d_struct = min(1, rms/0.25)`, `d_lum = min(1, |log2((m_c+0.02)/(m_r+0.02))|/1.0)`, `d_b = max(d_struct, d_lum)`, `d_b < 0.15 → 0`, D = mean of d_b; monochrome candidate (≥ 99.9% one value) while reference is not → D = 1 — [evalBase/examples/toy/scorer.py:1-24, 33-39, 70-112](evalBase/examples/toy/scorer.py)
- Toy procedural checks: `query:<name>` numeric within 1e-3 rel/abs, errors/None exact; `error_codes` whole stream with consecutive duplicates collapsed — [evalBase/examples/toy/scorer.py:129-170](evalBase/examples/toy/scorer.py)
- Toy perturbations `halfsamples` and `jitter` (camera shift 1/256 of the image), both tolerated; measured T: public 0.030 (x4), 0.048, 0.089, 0.235; hidden 0.030 (x5) … 0.300 (one case at cap) — [evalBase/examples/toy/docs/DESIGN.md:36-50](evalBase/examples/toy/docs/DESIGN.md)
- Toy limitation: spatially uniform noise makes D "almost bimodal"; "A real oracle's output has spatially varying noise and a graded T" — [evalBase/examples/toy/docs/DESIGN.md:99-107](evalBase/examples/toy/docs/DESIGN.md)
- Skill: "Compare in the space the consumer perceives, not in raw values. For images that meant a perceptual colour space after tonemapping, on blocks, at reduced resolution" — [metric.md:19-23](.claude/skills/lab-ready-eval/references/metric.md)
- Optional `preview_rgb8` / `block_defects` for workspace previews and heatmaps; `None` means numbers only — [evalBase/NEW_EVAL.md:113-115](evalBase/NEW_EVAL.md)
- Unit-test the distance: identical 1.0, gain low, noise at reference level > 0.9, shifted low — [evalBase/template/README.md:46-47](evalBase/template/README.md)

### Inferences
- **Toy constants are far too lenient for a deterministic rasterizer** (computed from scorer.py:33-38): a uniform offset δ in a block gives `d_struct = δ/0.25`, below the 0.15 floor for δ < 0.0375 (≈ 9.6/255); `d_lum` at mean 0.5 stays below 0.15 for δ < ~0.057. So bias errors up to ~9 LSB, 1-LSB rounding differences, most half-texel sampling shifts in smooth gradients, and isolated edge-coverage errors all score D = 0. Also the 2x downsample exists only to average MC noise and would blur single-pixel coverage errors; drop it.
- **Proposed Vulkan image distance** (per attachment, per channel, in the format's own units): e = |ref − cand| in LSBs (UNORM/SNORM: ×(2^bits−1); float formats: ULP distance, or relative error with an absolute floor for values near 0; sRGB formats compared in encoded space, which is already perceptually uniform); per block (e.g., 8x8, no downsample): `d_struct = min(1, rms(e)/S)`, `d_bias = min(1, |mean signed e|/B)`, `d_cov = min(1, frac(texels with e > K)/C)` (catches edge shifts and half-pixel errors that are sparse but large), `d_b = max(...)`, floor at the level the tolerated perturbations produce (e.g., ≤1 LSB rounding → 0). Integer formats and stencil: exact; `d_b = 1` if any texel in the block differs. Depth: D16/D24 in LSB, D32F in ULP. NaN/Inf class mismatch → texel error = max. Alpha graded as its own channel. Constants S, B, K, C must be set by the controls (`round_trunc` sets the floor honestly; `gain`, `half_pixel`, `nearest_filter`, `srgb_mishandled` must land well above T).
- **Multiple attachments / buffers**: one composite primary-channel file per snapshot (all color attachments, depth, stencil, and designated storage buffers, with format/layout metadata), `load_output` returning a dict, `distance = max` (or weighted mean) over parts; weighted mean is kinder to a candidate that gets depth slightly wrong, max makes every part a gate. `preview_rgb8` tone-maps float formats (e.g., clamp/Reinhard) and false-colours depth/stencil so the model sees pictures in `dev/reference/`.
- **Buffers (compute)**: typed per-binding comparison (layout declared in the case): ints exact, floats ULP-with-floor plus signed-bias term; the "block" becomes a fixed-size chunk of elements so D stays a fraction in [0,1].
- **Perturbations that plausibly define tolerance for SwiftShader** (each is a hypothesis to be measured; the skill says to measure each member's effect before adding it):
  - `subzero` (backend swap LLVM ↔ Subzero): the closest analogue of "second seed" — two SwiftShader builds that Google ships as equally valid. Tolerate.
  - `threads` (different worker count / affinity via `sample_mult=2` or a separate perturbation): expected D = 0; use as a determinism assertion, not to widen T; any non-zero case is flaky and removed or canonicalised.
  - `vtxjitter` (vertex nudge below subpixel precision) for raster families: tolerated; admits a candidate whose snapping differs only on exact-boundary samples.
  - `texcoord_ulp` (sampling coordinates nudged by 1 ULP): tolerated for filtering families; admits different but valid interpolation-weight rounding.
  - `lavapipe` (a different conformant CPU implementation): run and recorded, NOT tolerated — the fairness number. If a conformant implementation scores poorly, the metric is measuring SwiftShader idiosyncrasy, which the report must state.
  - `-ffast-math` / FMA-contraction builds: no such option in SwiftShader's top-level CMake (per the fetched CMakeLists), so this would need a custom patched build; likely not worth it — keep as untolerated if built at all.
  - Cross-CPU ISA (x86-64 vs aarch64 via `EVALBASE_PLATFORM` emulation, containers.py:183-184): measure as an open item, do not tolerate.
- **Tension with the Vulkan spec**: Vulkan defines precision bounds (ULP tolerances for float ops, implementation-defined subpixel bits, filtering precision), so a conformant candidate can differ from SwiftShader. Rule 4 forbids a tolerance "from a constant"; the reconciliation is to (a) freeze SwiftShader's implementation-defined choices in `spec/` (device profile: limits, subPixelPrecisionBits, mipmapPrecisionBits, format features) so the task is "match *this* implementation", and (b) report the `lavapipe` fairness number so readers see how much is SwiftShader-specific.

### Gaps
- No measurements exist yet: the actual defect of `subzero` vs `llvm`, of `vtxjitter`, or of `lavapipe` vs SwiftShader under the proposed distance are unknown, so the T distribution (the skill's "single most informative number") cannot be predicted.
- The right S/B/K/C constants can only be set after the controls are measured.

## Q4. Practical concerns: sandbox, build time, allowed dependencies, loader/ICD manifest, oracle determinism, 12 h budget, host cores

### Takeaway
Mechanically everything fits evalBase's Docker model (no network, labelled containers, CPU/memory limits), but four decisions dominate: (1) what the solver image contains (LLVM? SPIRV-Tools? validation layers?), (2) keeping fidelity cases sub-second so slow-but-correct candidates are not timed out, (3) asserting oracle determinism case by case, and (4) enforcing "no vendoring" by the image contents, since SwiftShader's source is not reachable without network but is plausibly memorised.

### Cited Findings
- Sandbox: one container per attempt, pinned image, compilers, no network, fixed CPU/memory (4 cores / 8 GB worked); agent runs on host, only tool calls enter the sandbox; the container never sees hidden corpus, reference cache, grader source or credentials — [references/harness.md:5-13, 24-34](.claude/skills/lab-ready-eval/references/harness.md)
- Oracle built from source in Docker, base image pinned by digest, apt packages pinned; image id recorded in every report; reference wall times measured on idle host at cache build and reused — [task-and-oracle.md:36-47](.claude/skills/lab-ready-eval/references/task-and-oracle.md)
- Template checklist: "Build it [the driver] into the trusted image; ship only the binary in the solver image"; "Build the solver image (toolchain + driver binary, unprivileged user, no oracle, no grader source)" — [evalBase/template/README.md:23-25, 65-67](evalBase/template/README.md)
- "No vendoring escape hatch. Forbid linking the real thing or its dependencies" — [task-and-oracle.md:30-32](.claude/skills/lab-ready-eval/references/task-and-oracle.md)
- 12 h budget, submit policy — [SKILL.md:79-82](.claude/skills/lab-ready-eval/SKILL.md), [evalBase/README.md:101-104](evalBase/README.md); two 4-core sandboxes on a 12-core host — [SKILL.md:128-131](.claude/skills/lab-ready-eval/SKILL.md); never run sweeps alongside attempts; finals graded idle — [references/attempts.md:21-24, 37-39](.claude/skills/lab-ready-eval/references/attempts.md)
- Whole reference cache should rebuild in about an hour; per-case reference runtime seconds — [task-and-oracle.md:61-62](.claude/skills/lab-ready-eval/references/task-and-oracle.md)
- ICD selection by `VK_ICD_FILENAMES` → `vk_swiftshader_icd.json`, or renaming the library to `vulkan-1` — [google/swiftshader README](https://github.com/google/swiftshader)
- SwiftShader bundles LLVM 10.0 by default and defaults to the LLVM Reactor backend — [swiftshader CMakeLists.txt](https://raw.githubusercontent.com/google/swiftshader/master/CMakeLists.txt)
- SwiftShader's JIT is considered a security risk in Chrome's GPU process — [chromestatus Remove SwiftShader fallback](https://chromestatus.com/feature/5166674414927872)

### Inferences
- **Images.** Reference image: SwiftShader (LLVM and Subzero builds, pinned commit), Vulkan loader, `vkreplay`, validation layers, glslang/SPIRV-Tools, optional lavapipe; built once, digest recorded. Solver image: gcc/clang, CMake, Ninja, Python, Vulkan headers + loader, `vkreplay` binary, SPIR-V disassembler (debugging aid), optionally the validation layer; *no* SwiftShader, no Mesa, no other Vulkan ICD, no SwiftShader source/headers. An `isolation_check` (TaskSpec) can assert `! find / -name 'libvk_swiftshader*'` and no `*lvp*`/Mesa ICD JSON in the solver image.
- **LLVM decision.** Allowing a pinned system LLVM lets candidates JIT (big performance-category advantage; SwiftShader itself uses LLVM, so LLVM is a *dependency*, and the "no vendoring ... or its dependencies" rule would literally forbid it). Recommendation: forbid for A/B/D (the from-scratch spirit and rule text), or offer as an explicitly separate variant; allow SPIRV-Headers (data only) but not SPIRV-Tools' optimizer as a linked library (parsing SPIR-V is part of the task). Validation layers in the solver image are harmless and help the model debug, since they implement no rendering.
- **Loader / manifest.** Simplest trusted path: the driver writes an `icd.json` pointing at `/candidate/build/libvk_candidate.so` and sets `VK_ICD_FILENAMES` (or newer loader `VK_DRIVER_FILES`, not verified here) before `vkCreateInstance`; the candidate must export `vk_icdNegotiateLoaderICDInterfaceVersion` / `vk_icdGetInstanceProcAddr`. Document this in `task/SPEC.md`, since a candidate that fails negotiation scores the stub band.
- **Build time.** A from-scratch candidate (tens of kLOC after 12 h) builds in minutes on 4 cores; F (full SwiftShader with LLVM) is far longer — ship a pre-built tree or ccache for F. The grading build runs in a clean sandbox; confirm its timeout (gap in Q1).
- **Determinism of the oracle.** Expected deterministic for fixed inputs on one host in graphics (Vulkan requires primitive-order blending) and in compute without order-dependent atomics; nondeterministic sources to exclude or canonicalise: float atomics/atomic counters with order-dependent return values, timestamp values, pipeline-statistics counts if implementation-defined, uninitialised memory reads (only arise from invalid usage, which generators must not produce). Assert per case via the n1/n2 runs.
- **Time/cores.** Cache rebuild cost ≈ cases × (2 + number of perturbations) oracle runs; with ~300 cases × 5 runs × ~1 s ≈ 25 min plus container overhead — within the "about an hour" guidance if per-case reference time stays around a second. Perf cases (≥2 s each, five repeats for the variance report) dominate.

### Gaps
- Whether the SwiftShader oracle is bit-deterministic across runs with different thread counts was not verified from primary sources.
- Exact build time for SwiftShader or for candidate code on the target host is unmeasured.
- Loader environment-variable naming in the pinned loader version (`VK_ICD_FILENAMES` vs `VK_DRIVER_FILES`) not verified.

## Q5. Risks: contamination, task size vs saturation, flakiness

### Takeaway
Contamination is the distinctive risk: SwiftShader (Apache 2.0, public on GitHub) and its design are almost certainly in training data, and the hidden split defeats memorised *outputs* but not memorised *implementation*. Saturation risk is inverse to scope: B/C/E alone may saturate; A is over-scoped as the skill demands. Flakiness risk is low for rendering but real for atomics, timing, and the performance category.

### Cited Findings
- SwiftShader is public, Apache 2.0 — [google/swiftshader](https://github.com/google/swiftshader)

### Inferences
- **Contamination is partly benign by design**: the eval measures behavioural fidelity to SwiftShader, so recalling SwiftShader's actual approximations (e.g., its transcendental approximations, rounding choices) raises scores legitimately-looking but via memory. Mitigations: (1) grade behaviour on a hidden split (defeats output memorisation); (2) report a source-similarity audit of final submissions against SwiftShader source (token/winnowing overlap) as a contamination indicator, not a penalty; (3) weight families where SwiftShader's behaviour is determined by the Vulkan spec rather than SwiftShader idiosyncrasy; (4) the `lavapipe` fairness number shows how much score depends on SwiftShader-specific choices. F is the worst case (the exact upstream diff is public).
- **Saturation**: B (SPIR-V compute interpreter) and C (sampler/formats) are well-specified and could be largely solved in a day by strong models; keep them as families inside A, or add exotic tails (float controls, 8/16/64-bit types, subgroups, compressed formats, cubic/anisotropic filtering, border colours) and a meaningful performance weight. A (full ICD) risks the opposite (floor effects) for weaker models; mitigate with a graded pyramid of families so early milestones (instance/device/buffer/compute) earn continuum credit.
- **Performance category risk**: SwiftShader is a highly optimised JIT; any from-scratch interpreter will be many times slower. With `perf_half=16` and `perf_gate=8`, most candidates would score ~0 on performance and never reach full success; either rescale (e.g., perf_half 64, gate 32) after measuring an interpreter control, or keep 16/8 and accept that full success requires a JIT. This is a design decision to log in DESIGN.md before calibration.
- **Flakiness sources**: multithreaded atomics, timestamps, JIT warm-up in timed runs, host load during attempts (grade finals idle), container overhead in sub-second timings (why timed runs must be ≥2 s).

### Gaps
- No public evidence found on how well current coding models reimplement Vulkan drivers or SPIR-V executors; saturation predictions above are inferences from the skill's calibration history, not measurements.
- No measured estimate of how much of SwiftShader's code models can reproduce verbatim.
